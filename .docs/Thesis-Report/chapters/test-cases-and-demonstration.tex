\section{Test strategy and summary}
\label{sec:test-strategy}

The strategy has four parts.
\begin{itemize}
  \item The ranking code is pure, so it is tested without a database: the same input must give the same output.
  \item The app is tested as a whole on a real PostgreSQL and a real Redis. The integration tests start the real app, and the Socket.IO tests connect real clients.
  \item One test ties the two parts together. The parity test checks that the live feed gives the same order as the evaluation harness (test case TC-07).
  \item The frontend has no automatic test. It is checked by hand in Chrome, and at the end by the rehearsal of the demo.
\end{itemize}

The first six rows are automatic tests: 1,025 tests in all, and all of them pass. The replay, the sweep and the rehearsal are checks that a person starts, so we count them apart. The parity test and the integration tests need \texttt{docker compose up db redis -d}, and the parity test also needs \texttt{syn-W2M-M} loaded into the schema \texttt{eval\_load}.

Two things are not tested. No test measures the speed of the feed or the delay of a socket message. The cost of one feed page is measured in experiment E7 (Section~\ref{sec:results-e7}), and the thesis sets no delivery time target (NFR4 in Table~\ref{tab:design-nfr}). And there is no browser test suite, so the frontend is covered only by what a person sees in Chrome.

\section{The bugs the tests found}
\label{sec:test-bugs}

The tests and the checks found 48 problems in the app. First a code review listed 26 suspected problems. Then we ran the app (curl scripts, Socket.IO scripts and Chrome). The run confirmed 25, half confirmed 1, and found 10 new ones: 36 findings. The fixes found 7 more small items (R1 to R7), and the demo sweep found 5 (V1 to V5). Of the 48 problems, 40 are fixed and 8 are open. The numbers come from the Bugs Report of the project (\texttt{.docs/Bugs Report.md}, section 1).

Each fix started with a test that failed. The same curl script gave 42 passed and 53 failed on the code before the fixes, and 95 passed and 0 failed after them. The bugs of the thesis path are covered by test cases of this chapter: the clock in Explore (T4) by the \texttt{asOf} tests, the stale feed cache (T3) and the duplicate follow (T6, in the feed) by \path{feed-algo.it-spec.ts}, and the socket rooms (S1) by TC-11.

The 8 open items are future work (Chapter 9): the missing unique keys of likes, saves and follows (T6) with the three items that need the same migration (N3, N10 and the schema part of R4), and four small items (R5, N7, N9 and B8). The six items that were needed before the app is put on a shared server (B1, S4, S6, B5, R3 and R6) are fixed, for example the fallback token secret (S6) and the missing check of moderation actions (B1). For R3, the packages, only the updates that need no major version were made. The others need NestJS 12 and Fastify 5, and they are future work (Chapter 9). T6 is the only open item on the thesis path. It can make duplicate rows, but the social feed counts each followee once, and a test checks this (``T6: a follow stored twice counts once (social)'').

\section{Demonstration}
\label{sec:test-demo}

The demo runs on generated data, not on the development data. The command \texttt{npm run demo:start} loads the dataset \texttt{syn-W2M-M} (1,000 users) into its own Postgres schema \texttt{eval\_demo}. The loader moves all times by one constant (\texttt{--rebase-to}), so that the newest event has the time of the start. Without this, Explore, which looks at the last 7 days, would be empty. The demo uses Redis database 3, so the development data (schema \texttt{public}) and the parity data (schema \texttt{eval\_load}, Redis database 2) are not touched. The command also adds one admin account (\texttt{demo\_admin}), starts the backend and the frontend, and prints the logins. It took 17 seconds in the rehearsal.

Two users play the demo. The long-history user \texttt{u0000000064} has 28 positive actions before the start time and follows 426 users. The little-history user \texttt{u0000000787} has 2 positive actions and follows 273 users. The password of both is \texttt{password}. The checklist \path{scripts/demo/CHECKLIST.md} has the steps with their expected results, for two browser windows: a normal one and a private one, each with its own cookies. The rehearsal of 2026-11-22 played every step, and all nine passed (Table~\ref{tab:test-levels}). The screenshots below come from the same demo. Only one browser session was available, so a script (\path{peer.mjs}) played the second user; in the real demo, the second user has a second window.
