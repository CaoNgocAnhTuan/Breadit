This chapter designs the platform of contribution C1 (the architecture) and contribution C3 (the real-time layer), and shows where the ranking of C2 plugs in. Section~\ref{sec:design-requirements} lists the requirements. Section~\ref{sec:design-usecases} gives the use cases. Chapter 3 defines the ranking method, so this chapter only shows where the method is called. Chapter 5 describes how the design is built. Every route, guard and field named here was checked against the code.

\section{Use cases}
\label{sec:design-usecases}

The platform has four actors. A \textbf{Guest} is not signed in. A \textbf{User} is signed in. A \textbf{Community owner or moderator} is a User who has the role OWNER or MOD in one community. An \textbf{Admin} has the role ADMIN. The email service (SMTP) is a system actor that sends the codes. Figure~\ref{fig:design-usecase} shows the use cases of each actor.

\begin{figure}[htbp]
  \centering
  \thesisdiagram{fig4-1-usecase}{\textwidth}
  \caption{Use case overview.}
  \label{fig:design-usecase}
\end{figure}

The web app sends a guest to the sign-in page for every page except sign-up, verify, sign-in, forgot password and reset. So the Guest has only three use cases in the figure. Some API routes also accept a guest (they use \texttt{OptionalJwtAuthGuard}), but the web app does not use them for guests, so we leave them out. The admin routes need the role ADMIN.

We specify four use cases in detail (Tables~\ref{tab:design-uc-feed} to~\ref{tab:design-uc-ban}). They are the ones the thesis relies on: the For You feed with the option \texttt{algo} (C2), a direct message (C3), joining a community and posting in it (a post in a community needs membership, which the community term of the score assumes), and banning a user (the admin control, and a second real-time event). The other use cases follow the same pattern: a chain of guards, one service call, and often a notification.

\section{Activity diagrams}
\label{sec:design-activity}

Three activity diagrams show the flows that have decisions: sign up, publish a post, and get one page of a feed. The other flows are simple chains, and the use cases above describe them.

Figure~\ref{fig:design-signup} shows the sign-up. The form needs a username of 3 to 30 letters, digits or underscores, a valid email and a password of at least 6 characters. A wrong input gives 400. A username or an email that is already in use gives 409. Then the backend hashes the password with bcrypt and creates the user with \texttt{emailVerified} empty.

Next, the backend makes a 6-digit code that is valid for 15 minutes, saves it in the \texttt{VerificationToken} table and sends it by email. If the email cannot be sent, the error is only logged: the user exists and can ask for a new code, which replaces the old one. The resend route gives the same answer whether or not the email is known, so it does not tell who has an account.

After the right code, the backend sets \texttt{emailVerified}, deletes the code, and the user goes to the sign-in page. An unverified user can sign in, but \texttt{EmailVerifiedGuard} refuses the main writes. The register and verify routes allow 10 requests per minute, and the resend route allows 5.

  \centering
  \thesisdiagram{fig4-2-signup}{\textwidth}
  \caption{Sign up with email verification.}
  \label{fig:design-signup}
\end{figure}

Figure~\ref{fig:design-publish} shows how a post is published. Three guards run first: signed in, not banned (read from the database) and email verified. Then the service checks the text (at most 255 characters, and text or media). For a community post, it also checks that the community exists, that the user is not banned there and that the user is a member.

Only then are the files uploaded (to Cloudinary or to the local disk) and the post saved. The field \texttt{isApproved} is true outside a community. In a community, it is true only for the owner or a moderator, so the post of a member waits for approval. The service then raises the \texttt{v:user} version of the author, so the new post shows at once in the author's own feeds.

When the post has text, the service saves its hashtags in lower case and its mentions. A mention is saved only for a user whom the author follows, and that user gets a MENTION notification. For a community post, the other members are notified when an owner or a moderator posts (COMMUNITY\_NEW\_POST), and the owners and the moderators are notified when a member posts (COMMUNITY\_POST).

\end{figure}

Figure~\ref{fig:design-feedpage} shows how one page of a feed is made. It is the place where the ranking plugs in. The request has a cursor and the options \texttt{feed}, \texttt{user}, \texttt{communityId}, \texttt{algo} and the test-only \texttt{asOf}. The backend first checks the options. \texttt{algo} is allowed only on For You and only for a signed-in user, and \texttt{asOf} only when a test flag is on. A wrong option gives 400 or 401. A signed-in user on For You with no \texttt{algo} gets the default of the configuration.

Then the clock is read once, and the cache key is built from the viewer, the mode, the cursor, the \texttt{v:user} version and \texttt{asOf}. A cache hit returns the page. On a miss, an \texttt{algo} feed asks \texttt{FeedService.rank} for the ranked pool at time $t$, and takes the 10 posts after the cursor. The other modes run one database query: community, Explore, Following, Communities, profile, For You (newest first) or guest.

These queries leave out deleted posts and blocked users, and community posts appear only in the community feeds and only when approved. Explore scores its 400 newest candidates with the engagement score of the ranking package. Every page is stored for 10 seconds.

\section{Sequence diagrams}
\label{sec:design-sequence}

Four sequence diagrams show the order of the calls between the components: the session, a notification, a direct message and the social feed. The first three are the pattern of the real-time platform. The last one is the new part of the thesis.

Figure~\ref{fig:design-session} shows the session. At sign-in, the backend finds the user by email and compares the password with the bcrypt hash. A wrong email or password gives 401. Otherwise it signs a token with HS256, a new \texttt{jti} (a unique token id) and a life of 30 days, and sets it in the httpOnly cookie \texttt{breadit\_session}. The token holds the id, the username, the email, the \texttt{emailVerified} date, the role and the \texttt{banned} flag. Sign-in does not refuse a banned or an unverified user; the guards stop their writes later.

On every later request, \texttt{JwtAuthGuard} verifies the token, asks Redis whether \texttt{auth:blacklist:<jti>} exists, checks that the password version in the token (claim \texttt{pwv}) is the user's current one, and fills \texttt{req.user}. At sign-out, the backend stores that key in Redis for the rest of the token's life, so the list cleans itself. A request with the old token then gets 401. A password reset adds 1 to the user's password version, so every token made before it gets 401 in the same way.

  \centering

  \caption{Sign in, a signed-in request and sign out.}

Figure~\ref{fig:design-like} shows the pattern of every notification: a guard chain, a service call, the change in the database, and then \texttt{NotificationsService.emit}. Alice likes Bob's post. The post must exist, must not be deleted, and Alice must be allowed to see it (a post that waits for approval is open only to its author and the community owner and mods), or the answer is 404. A like is a toggle: a second call deletes the like and sends nothing. A new like calls \texttt{emit} without waiting for it, so the answer to Alice does not depend on the push. \texttt{emit} skips a like of your own post, saves a \texttt{Notification} row, finds the username of Bob, and sends \texttt{getNotification} to the room of that username. The room is the address of the user, and the Redis adapter makes it work with more than one backend process. The service reads the like count after the change and returns it.

Figure~\ref{fig:design-dm} shows a direct message. When Bob's page loads, his socket connects with the cookie. The gateway checks the cookie, the blacklist and the password version, and joins the socket to the room named after Bob. The server decides this, and the name that the client sends is ignored (finding S1). When Alice sends a message, the guards run, and the service checks that Alice is a member of the conversation and that no block exists between the two. If not, the answer is 403. Otherwise the service writes the message and the conversation time in one transaction. Then it pushes \texttt{newMessage} to the room of Bob, deletes the cached unread count of Bob for this conversation, and answers 201 with the message. Typing signals use the rooms \texttt{conversation:<id>}, and a socket can join such a room only if it is a member.

Figure~\ref{fig:design-social} shows the new part of the thesis inside the platform. On a cache miss, \texttt{PostsService} asks \texttt{FeedService.rank} to rank the pool for the user at time $t$. The time $t$ is \texttt{asOf}, the time inside the cursor (page 2 and later), or the clock. \texttt{FeedService} loads plain data from Postgres in four steps: the root posts of the window $[t - W, t)$, with community posts included; the follows, the memberships and the earlier positives of the user; the blocked peers; and, once the pool is built, the likes, comments and reposts on the pool posts. All events are taken before $t$. Between the loads, it calls the ranking package, which returns the post ids in order.

\texttt{PostsService} takes the 10 posts after the cursor, loads them with their counts and media, and stores the page for 10 seconds. The cursor \texttt{t:score:id} holds $t$, so page 2 is ranked at the same time as page 1, and no post repeats or is skipped. Sections~\ref{sec:method-protocol} and~\ref{sec:method-hybrid} define the pool and the score.

\section{Architecture and modules}
\label{sec:design-architecture}

Figure~\ref{fig:design-components} shows the components of the platform.

\begin{figure}[htbp]
  \centering
  \thesisdiagram{fig4-9-components}{\textwidth}
  \caption{The components of the platform.}
  \label{fig:design-components}
\end{figure}

\textbf{Frontend.} The frontend is a Next.js 15 app with React 19. It has no database and no API routes of its own: all data comes from the backend over \texttt{/api/...}. A middleware only checks that the session cookie exists, and sends the user to the sign-in page if it does not. The backend does the real check. Server components fetch data with \texttt{serverFetch()}, which calls the backend by its internal address and forwards the cookie. Client components use TanStack Query and \texttt{api()}, which calls the backend from the browser with the cookie. One Socket.IO connection is shared by the whole page.

\textbf{Backend.} The backend is NestJS 10 on Fastify. It has 13 controllers with 72 REST routes, all under \texttt{/api/...}, and one Socket.IO gateway in the same process. A request passes the rate limiter, the validation pipe, the guards written on the route, the controller and the service. One filter turns every error into the same JSON shape. The services work on PostgreSQL through Prisma 6, and push events through the gateway.

\textbf{Data services.} PostgreSQL 16 is the system of record. Redis 7 has four jobs: the JSON cache, the logout blacklist, the store of the rate limiter and the adapter of Socket.IO. Uploaded files go to Cloudinary when it is configured, and to the local disk if not. Emails go out through an SMTP server.

\textbf{Real-time layer.} The gateway gives each socket the user of its cookie, and puts it in a room named after the username. A service sends an event to a user with \texttt{server.to(username).emit(...)}. Table~\ref{tab:design-events} lists the events. A notification is saved before it is pushed, so an offline user finds it later in the list. The feed is not pushed: it is ranked when the user opens or reloads it.

\textbf{Cache.} Read-heavy endpoints keep their JSON answer in Redis under a key such as \texttt{feed:<viewer>:<mode>:...}. One part of the key is a version number, for example \texttt{v:user}. A write raises the version, so later reads build a new key and miss the cache. The old entries are never deleted, and they expire. We chose versions because one write can change many cached pages whose keys are not known in advance. Feed pages live 10 seconds. The likes and comments of other users do not raise your version, so your feed can be up to 10 seconds old. This is the price of a simple cache. The cost experiment E7 runs with the cache off, to measure the ranking work.

\textbf{Rules for every listing.} Post, user, search, notification and message listings leave out blocked users in either direction. A soft-deleted post (\texttt{deletedAt}) is never shown. A community post is shown only when it is approved. Hashtags and mentions are read when a post is saved, so reading never parses text.

Figure~\ref{fig:design-boundary} shows the one boundary that C2 adds. The backend loads plain arrays from PostgreSQL, calls five functions of the package (\texttt{user\allowbreak Features\allowbreak AsOf}, \texttt{post\allowbreak Features\allowbreak AsOf}, \texttt{buildPool}, \texttt{scorer} and \texttt{rankPool}) and gets back post ids in order. The package is pure: it has no Nest, Prisma, Redis, clock or randomness, and the time $t$ is an argument. The Explore feed calls \texttt{computeExploreScoreFixed} of the same package; this is the method BL2. The offline evaluation in \texttt{eval/} calls the same functions with data from CSV files.

  \centering
  \thesisdiagram{fig4-10-ranking-boundary}{\textwidth}
  \caption{The boundary of the ranking package.}
  \label{fig:design-boundary}
\end{figure}

This is the main design rule of the thesis: all ranking logic lives in the package, and never in the backend. We keep the score out of SQL and out of the services, because two copies of one rule could drift apart. With one copy, a number measured offline describes the live feed, and a parity test checks that the live order equals the order of the evaluation (Section~\ref{sec:method-repro}).

\section{Database design}
\label{sec:design-database}

The database is PostgreSQL 16, used through Prisma 6. The schema has 25 models. Figure~\ref{fig:design-erd} shows 23 of them, with their links. \texttt{Account} and \texttt{Session} are left out, because no code reads them. The figure shows only the name of each table; the fields of each table are in Appendix C, in four groups (Figures~\ref{fig:app-erd-users} to~\ref{fig:app-erd-communities}). Each line of the figure is one foreign key, named by its field. For example, the line from \texttt{User} to \texttt{Post} named \texttt{userId} means that one user has zero or more posts, and each post has exactly one user, through \texttt{Post.userId}. A line that may be empty on one side means that the foreign key can be empty: a post may have no community.
